# AGENTS.md

## Project Overview

This project is a private, single-user recipe application.

The app allows the owner to:

- Create and edit personal recipes.
- Save recipes found online.
- Import recipes generated by AI.
- Search, tag, favourite, and organise recipes.
- Access recipes from an iPhone, desktop browser, or other trusted device.
- Install the app as a Progressive Web App.
- Read recently used or locally cached recipes while offline.
- Create, update, and delete recipes while offline.
- Queue changes locally and upload them safely when connectivity returns and the PWA is reopened.

The application must be fast, mobile-first, simple to maintain, and free or very close to free for one user.

## Primary Architecture

Use the following stack unless a documented technical reason requires a change:

### Frontend

- React
- TypeScript
- Vite
- Progressive Web App
- `vite-plugin-pwa`
- Dexie for IndexedDB
- A small custom iOS-inspired design system
- CSS Modules, plain CSS, or another lightweight styling approach
- React Router where routing is useful

### Backend

- Cloudflare Workers
- Cloudflare D1
- Cloudflare Access
- Cloudflare R2 only if image storage is added
- Cloudflare-hosted static assets or Pages/Workers static assets

### Deployment model

- The frontend app shell may be publicly retrievable so it can launch reliably offline.
- Every API endpoint must be protected.
- All recipe data must stay in authenticated API responses, D1, R2, or local IndexedDB.
- No personal recipe data may be embedded in public JavaScript, HTML, build files, or static JSON.

## Core Product Principles

1. Local-first user experience.
2. Server-backed durability.
3. Authentication on every API request.
4. No implicit trust in frontend state.
5. No silent data loss.
6. Safe retries for all queued writes.
7. Fast rendering from IndexedDB.
8. Simple single-user operation.
9. Security over convenience when the two directly conflict.
10. Exportability and avoidance of vendor lock-in.

## Security Requirements

Security requirements are mandatory. Do not weaken them to simplify implementation.

### Authentication

All API requests require authentication.

This includes:

- `GET`
- `POST`
- `PUT`
- `PATCH`
- `DELETE`
- File upload endpoints
- Import endpoints
- Search endpoints
- Export endpoints
- Synchronisation endpoints
- Health or metadata endpoints that expose application or user information

A route must be considered private unless it is explicitly documented as public.

The static PWA shell may be public, but it must contain no private data.

### Cloudflare Access

Use Cloudflare Access as the primary authentication layer.

Restrict access to the owner's approved email address.

Configure the longest practical session duration supported by Cloudflare Access so the trusted device does not require frequent reauthentication.

The Worker must independently validate the Cloudflare Access JWT. Do not rely only on Cloudflare's outer routing configuration.

Validate:

- JWT signature
- Issuer
- Audience
- Expiration
- Not-before time where applicable
- Approved identity or email claim
- Required application audience
- Token structure

Reject missing, expired, malformed, or invalid tokens.

Use the `Cf-Access-Jwt-Assertion` header or the officially supported Cloudflare Access token mechanism.

Do not trust identity information sent by the frontend in the request body.

Do not accept a user ID, email address, or role from the client as proof of identity.

### Access tokens

A valid access token is mandatory for every authenticated API request.

For state-changing requests, also require:

- The correct HTTP method
- A valid `Content-Type`
- A valid Cloudflare Access token
- CSRF protection where cookie-based authentication could allow a cross-site request
- Strict Origin or Referer validation where appropriate
- Input validation
- Authorisation checks
- Idempotency handling
- Reasonable request size limits

Never put permanent service tokens, private API keys, Cloudflare secrets, database credentials, or signing secrets in frontend code.

Never store sensitive tokens in `localStorage`.

Prefer secure, `HttpOnly`, `Secure`, and appropriate `SameSite` cookies where a cookie is needed.

### Authorisation

Although the application currently has one user, authorisation must still be explicit.

The backend must verify that the authenticated identity is the approved owner before reading or mutating data.

Do not rely on hidden URLs, frontend route guards, or obscurity.

Every recipe read and write must be checked server-side.

Do not assume that single-user applications do not need authorisation.

### API defaults

Use a deny-by-default approach.

Unknown routes must return a safe `404`.

Unsupported methods must return `405`.

Unauthenticated requests must return `401`.

Authenticated but unauthorised requests must return `403`.

Validation errors must return `400` or `422`.

Do not expose stack traces, SQL statements, secret values, internal paths, or Cloudflare configuration in production error responses.

### CORS

Use a strict CORS allowlist.

Only allow the production app origin and explicitly approved local development origins.

Do not use `Access-Control-Allow-Origin: *` for authenticated endpoints.

Only allow required methods and headers.

Reject unexpected origins.

### CSRF

If authentication depends on cookies, protect state-changing requests against CSRF.

Use one or more of:

- Strict `SameSite` cookie settings
- Origin validation
- Referer validation
- A CSRF token
- A custom required request header that cannot be sent by a normal cross-origin form

Do not assume Cloudflare Access alone automatically eliminates all CSRF risks.

### Input validation

Validate every request on the server.

Recommended approach:

- Use Zod or another explicit schema-validation library.
- Reject unknown or unexpected fields where practical.
- Enforce maximum lengths.
- Enforce valid UUID formats.
- Enforce numeric ranges.
- Enforce arrays with sensible maximum sizes.
- Enforce supported MIME types.
- Enforce upload size limits.
- Normalise text carefully.
- Never construct SQL with string concatenation.

Use parameterised D1 queries only.

### Output safety

Treat imported recipe content as untrusted.

Never render imported HTML directly.

Do not use `dangerouslySetInnerHTML` for recipe text.

Store and render plain text or a strictly sanitised subset.

Escape output by default.

Sanitise any rich-text format with a well-maintained library and a strict allowlist.

### Content Security Policy

Set a restrictive Content Security Policy.

Prefer:

- `default-src 'self'`
- No inline scripts
- No `eval`
- Restricted image origins
- Restricted connect origins
- `frame-ancestors 'none'`
- `base-uri 'self'`
- `form-action 'self'`

Adjust only when required and document every exception.

Also add appropriate headers such as:

- `X-Content-Type-Options: nosniff`
- `Referrer-Policy`
- `Permissions-Policy`
- `Strict-Transport-Security`
- `Cross-Origin-Opener-Policy` where appropriate
- `Cross-Origin-Resource-Policy` where appropriate

### Rate limiting

Apply reasonable rate limits to:

- Import-from-URL endpoints
- File uploads
- Synchronisation endpoints
- Authentication-sensitive endpoints
- Export endpoints

Rate limits are still useful for a single-user app because stolen sessions, mistakes, loops, or malicious sites can create abuse.

### URL import security

The recipe importer must treat remote URLs as untrusted.

Protect against server-side request forgery.

The importer must:

- Allow only `http` and `https`.
- Prefer `https`.
- Reject localhost.
- Reject loopback addresses.
- Reject private IP ranges.
- Reject link-local addresses.
- Reject cloud metadata endpoints.
- Reject internal Cloudflare or service addresses.
- Resolve and re-check DNS before connecting.
- Re-check redirects.
- Limit redirect count.
- Limit response size.
- Use strict timeouts.
- Reject unsupported content types.
- Parse only expected recipe metadata.
- Never execute remote scripts.
- Never forward authentication cookies or headers to the remote site.

Preserve source attribution and the original URL.

### Image upload security

If R2 image upload is implemented:

- Require authentication.
- Validate MIME type from file content, not only extension.
- Use an allowlist such as JPEG, PNG, WebP, or HEIC only if conversion is handled safely.
- Limit file size.
- Generate server-side object names.
- Never use raw user filenames as trusted paths.
- Strip metadata where practical.
- Avoid serving active content such as SVG unless sanitised.
- Return images with safe content types and headers.
- Prevent public bucket listing.
- Prefer signed or authenticated access if images must remain private.

### Secrets

Store secrets only in Cloudflare secret bindings or equivalent secure configuration.

Do not commit:

- Access secrets
- API keys
- Account identifiers that should remain private
- Signing keys
- Tokens
- Production configuration containing secrets
- `.dev.vars`
- `.env` files with secrets

Provide `.env.example` or `.dev.vars.example` files containing placeholders only.

### Logging and privacy

Do not log full access tokens.

Do not log entire recipe bodies by default.

Do not log uploaded file contents.

Do not log sensitive request headers.

Use structured logs with:

- Request ID
- Route
- Method
- Response status
- Duration
- Authenticated owner identifier in a privacy-conscious form
- Error code

Avoid exposing personal data in analytics.

### Dependency security

Keep dependencies minimal.

Pin versions where reasonable.

Run security audits.

Remove unused packages.

Do not install packages merely to save a few lines of code.

Prefer maintained libraries with active security support.

## Offline-First Requirements

### Local database

Use IndexedDB through Dexie.

IndexedDB stores:

- Recipes
- Ingredients
- Instructions
- Tags
- Favourites
- Source metadata
- Cached image references
- Synchronisation metadata
- Pending operations
- Failed operation information
- Last successful sync timestamps

Do not store unsynchronised changes only in memory or Cache Storage.

### Persistent storage

Request persistent browser storage using the Storage API where supported.

Check and expose the result in settings.

The UI should distinguish between:

- Persistent storage granted
- Best-effort storage only
- Storage API unavailable

Do not claim that browser storage can never be removed.

Warn before any local reset if unsynchronised operations exist.

### App shell cache

Use the service worker cache for replaceable static assets:

- HTML shell
- JavaScript
- CSS
- Icons
- Fonts supplied by the platform or allowed web assets
- Offline fallback assets

Do not use Cache Storage as the source of truth for recipe records.

### Offline launch

The app must:

1. Launch from the Home Screen without network access after it has been installed and opened successfully at least once.
2. Render the app shell from the service worker cache.
3. Render recipes from IndexedDB immediately.
4. Avoid blocking initial rendering on authentication or network requests.
5. Show clear online, offline, pending-sync, and authentication-required states.

### Local-first writes

All user writes must save locally first.

For create, update, or delete:

1. Validate on the client for usability.
2. Write the local entity change.
3. Write a corresponding outbox operation.
4. Commit both in one IndexedDB transaction.
5. Update the UI immediately.
6. Attempt network synchronisation when practical.

Do not display a change as safely saved until the IndexedDB transaction succeeds.

### Outbox rules

Every pending operation must include:

- Stable operation ID
- Entity ID
- Operation type
- Payload
- Creation time
- Last attempt time
- Attempt count
- Base server version
- Local version
- Current status
- Last error code if any

Never delete an outbox operation merely because a request was sent.

Delete or mark complete only after a valid authenticated server acknowledgement.

Do not discard an operation after a retry limit.

Retries may back off, but pending data must remain.

### Synchronisation triggers

Attempt synchronisation:

- At app launch
- When the app becomes visible
- When the browser reports that it is online
- After a successful login
- After a local change when online
- When the user presses `Sync now`

Do not depend on iOS background sync.

Queued operations must upload when the PWA is reopened and an authenticated connection is available.

### Idempotency

All write requests must be safely retryable.

Each write operation must include a stable idempotency key or operation ID.

The server must record processed operations.

If the same operation is received more than once, return the previous success result instead of applying the write twice.

Use a D1 table such as:

```sql
CREATE TABLE processed_operations (
    operation_id TEXT PRIMARY KEY,
    processed_at TEXT NOT NULL,
    response_json TEXT NOT NULL
);
```

The server must commit the domain write and processed-operation record atomically where possible.

### Conflict handling

Each recipe must have a server version.

Updates must include the client's base version.

If the server version changed since the client last synced:

- Do not silently overwrite.
- Return a conflict response.
- Keep the local operation.
- Show a conflict-resolution UI.
- Allow the owner to keep local, keep server, or merge fields.

For the first version, a simple last-edit comparison and manual resolution is acceptable.

### Sync ordering

Preserve operation dependencies.

A create must reach the server before updates or deletes for the same entity.

Operations for the same recipe must be processed in order.

Where safe, collapse multiple unsent updates into one latest update.

Never collapse across a delete in a way that changes intent.

### Authentication expiry during sync

If the API returns an authentication failure:

- Stop processing the outbox.
- Keep every operation.
- Show `Sign in to sync`.
- Do not redirect in a way that destroys app state.
- Resume automatically after successful authentication.

### Server as durable source

D1 is the durable source for synced data.

IndexedDB is the local-first working copy.

Do not assume unsynced local data has a server backup.

Provide a visible pending-sync count.

## API Design

Recommended endpoints:

```text
GET    /api/recipes
GET    /api/recipes/:id
POST   /api/recipes
PUT    /api/recipes/:id
PATCH  /api/recipes/:id
DELETE /api/recipes/:id

GET    /api/tags
POST   /api/tags

POST   /api/import/url
POST   /api/import/json

POST   /api/sync
GET    /api/sync/changes

POST   /api/images
DELETE /api/images/:id

GET    /api/export
```

Every endpoint above requires authentication.

Prefer a batch synchronisation endpoint once the basic CRUD API is stable.

All write endpoints must accept an idempotency key.

Use consistent JSON error responses:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "The request could not be accepted.",
    "requestId": "..."
  }
}
```

Do not reveal implementation details in error messages.

## Testing Requirements

Add automated tests for security and data integrity.

### Unit tests

Test:

- Validation schemas
- Sync queue ordering
- Update collapsing
- Retry behaviour
- Conflict detection
- Authentication middleware
- Authorisation checks
- URL validation
- SSRF protection
- Idempotency handling
- Version increments

### Integration tests

Test:

- All API routes reject missing authentication.
- All API routes reject invalid authentication.
- GET requests cannot expose recipes anonymously.
- POST, PUT, PATCH, and DELETE require valid tokens.
- Invalid origins are rejected where applicable.
- Duplicate operation IDs do not duplicate changes.
- Offline operations survive app restart.
- Failed writes remain queued.
- Expired authentication does not delete pending operations.
- Reauthentication resumes synchronisation.
- Imported HTML cannot execute scripts.
- SQL injection payloads remain data, not executable SQL.
- Oversized uploads are rejected.
- Private and loopback URLs are rejected by the importer.

### End-to-end tests

Cover:

- Installable PWA
- Offline launch
- Read cached recipe offline
- Create recipe offline
- Close and reopen app
- Restore network
- Upload queued change
- Authentication expiration
- Login and sync resume
- Conflict handling
- Export and restore

## Development Rules for Agents

Before changing code:

1. Read this file.
2. Inspect the existing project structure.
3. Read relevant tests.
4. Identify the security boundary.
5. Identify whether the change affects offline data or synchronisation.
6. Avoid broad unrelated refactors.
7. Preserve compatibility with the current deployment model.

When implementing:

- Use strict TypeScript.
- Avoid `any`.
- Validate at runtime at every external boundary.
- Keep server logic independent from UI logic.
- Keep sync code explicit and testable.
- Use parameterised SQL.
- Return typed errors.
- Add tests for every security-sensitive change.
- Add migrations rather than editing production schema manually.
- Keep commits focused.
- Document security decisions.

Before declaring work complete:

- Run formatting.
- Run linting.
- Run type checking.
- Run unit tests.
- Run integration tests.
- Build the production bundle.
- Check for accidentally committed secrets.
- Verify unauthenticated access fails.
- Verify offline data is not lost.
- Verify queued operations retry correctly.
- Verify no private data is included in static build output.

## Non-Goals for the First Version

Do not add these before core security and offline reliability are complete:

- Multiple users
- Social sharing
- Public recipe profiles
- Native iOS application
- App Store distribution
- Bank-style device authentication
- Paid AI integration
- Complex nutrition analysis
- Real-time collaboration
- Background sync that depends on unsupported iOS APIs
- Automatic scraping of every possible recipe website

## Definition of Done

A feature is complete only when:

- It works online.
- It fails safely offline.
- It does not lose queued data.
- It requires authentication where applicable.
- It has server-side validation.
- It has appropriate tests.
- It does not expose secrets.
- It has useful error handling.
- It preserves accessibility.
- It does not degrade PWA launch performance.
